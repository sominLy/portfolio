같은 사용자라도 실제 사용 과정에서 먼저 필요한 기능이 달라질 수 있어, 기능을 정하기 전에 사용 상황을 확인해야 했습니다.

PROJECT 03 · 시장에 가면

외국인이 음식 사진으로 판매처를 찾는 과정을
기능 명세와 화면 흐름으로 만들었습니다.

글로벌 커뮤니티 데이터를 분석해, 음식명을 모르면 사진으로 음식을 확인한 뒤 판매처를 찾는 행동을 확인했습니다. GPS로 음식과 점포를 연결하던 초기안 대신 이미지 탐색을 중심으로 기능과 화면 흐름을 설계했습니다. 점포 정보는 방문자의 사진 제보로 갱신하고, NFC 키링을 통해 서비스에 접속하도록 정리했습니다.

나의 역할분석 질문을 정하고 데이터를 분석했습니다. 확인한 행동을 기능 명세와 화면 흐름에 반영했습니다.
협업 방식유스케이스 18종에 예외 흐름과 화면별 기능을 적어 기획·디자인·개발팀이 같은 기준으로 확인하도록 했습니다.
프로젝트 결과유스케이스 18종과 기능 명세를 완성했고, LG DX School 장려상을 받았습니다.

PROJECT 04 · BLD.M

업무 맥락

메타버스 프로젝트가 빠르게 늘었지만 고객사와 제작팀 모두 관련 경험이 적어 요청 형식이 매번 달랐습니다.

확인한 문제

요구를 빠짐없이 전달하고 확인할 공통 문서가 없어 누락과 재질문이 반복됐습니다.

내가 만든 문서

  • 일정·기능·디자인을 나눈 표준 작업 의뢰서
  • 반복 QA를 유형화한 운영 매뉴얼
  • 행사마다 바꿀 항목과 공통 항목을 나눈 체크 기준

결과

초기 맵 기획 시간을 약 50% 줄였고, 팀이 3인에서 8인으로 커진 뒤에도 같은 문서를 사용했습니다.

작업 의뢰서고객 요청을 일정·기능·디자인 항목으로 나눠 제작 전에 확인했습니다.
QA 매뉴얼행사마다 반복된 질문과 수정 기준을 유형별로 기록했습니다.
협업 결과초기 맵 기획 시간을 약 50% 줄이고 팀 확대 후에도 같은 방식을 사용했습니다.
